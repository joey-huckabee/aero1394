# SAE AS5643 ASM profile

- Status: Provisional implementation contract based on explicit working assumptions
- Last updated: 2026-08-28
- Assumed base revision: SAE AS5643B; producing-system revision not confirmed
- Scope: AS5643 Anonymous Subscriber Message interpretation independent of capture format

## Purpose

This document defines the AS5643 Anonymous Subscriber Message (ASM) profile
used by Aero1394. It owns the logical ASM header, payload header, application
boundary, packet trailer, heartbeat behavior, STOF-relative timing fields, and
Vertical Parity Check (VPC) calculation. Input-container documents may map
stored bytes to these fields, but they do not redefine their AS5643 semantics.

SAE describes AS5643B as the base specification for data-bus characteristics,
data formats, and node operation, with vehicle-specific details delegated to a
network-profile slash sheet. The applicable producer revision and slash sheet
are not yet available. Aero1394 therefore adopts the explicit assumptions in
this document as its current implementation contract. They are testable design
decisions, not representations that the unavailable SAE text has been quoted
or independently verified.

Definitions below use these labels:

| Label | Meaning |
| --- | --- |
| Public structure | Shown by the official SAE description or DAP Technology's public AS5643 material |
| Working assumption | Aero1394 behavior selected to make the current profile implementable |
| Profile-defined | A value whose authoritative meaning ultimately belongs to the vehicle network profile |

## Protocol boundary

AS5643 interpretation begins with the logical ASM header carried by a supported
IEEE-1394 asynchronous-stream representation and ends after the AS5643 packet
trailer:

```text
IEEE-1394 asynchronous-stream packet
    -> AS5643 ASM header
        -> AS5643 payload header
            -> opaque application data
        -> AS5643 packet trailer
    -> IEEE-1394 data CRC
```

[`IEEE1394.md`](IEEE1394.md) owns the surrounding IEEE-1394 representation,
packet fields, and IEEE CRCs. [`PAYLOADS.md`](PAYLOADS.md) owns the application
data beginning at application offset zero. AS5643 decoding does not depend on
the source capture container or on a known application definition.

## Profile identity and selection

The profile defined by this document has the stable provisional identifier:

```text
aero1394-assumed-as5643b-v1
```

Every decoded result produced by this profile carries that identifier and
`assumption_dependent = true`. Profile selection must be explicit or based on
an input mapping that names this identifier; byte-pattern recognition alone is
insufficient. A later authoritative profile receives a new identifier rather
than silently changing these assumptions.

## Logical ASM layout

DAP Technology's public AS5643 layout shows a four-word ASM header, Health
Status as message-data word 0, Heartbeat as message-data word 1, application
message data, three STOF-offset trailer words, and VPC. Aero1394 represents
each AS5643 word as one big-endian unsigned 32-bit integer.

Let `M` be the application-data length in bytes and `P = M + 8` be the AS5643
payload length, including Health Status and Heartbeat. Logical offsets below
start at ASM-header word 0 and exclude the surrounding IEEE-1394 header, header
CRC, and data CRC.

| Logical ASM offset | Width | Field | Status |
| ---: | ---: | --- | --- |
| `0x00` | 4 | [Message ID](#message-id) | Public structure; encoding assumed `u32be` |
| `0x04` | 4 | [Reserved/security word](#reservedsecurity-word) | Public structure; bit allocation profile-defined |
| `0x08` | 4 | [Node ID](#node-id) | Public structure; bit allocation profile-defined |
| `0x0C` | 4 | [Priority and payload length](#priority-and-payload-length) | Public structure; bit split is a working assumption |
| `0x10` | 4 | [Health Status](#health-status) | Public structure; bit allocation profile-defined |
| `0x14` | 4 | [Heartbeat](#heartbeat) | Public structure; counter behavior is a working assumption |
| `0x18` | `M` | [Application data](#application-data) | Profile-defined |
| `0x18 + M` | 4 | [STOF Transmit Offset](#stof-transmit-offset) | Public structure; units and semantics assumed |
| `0x1C + M` | 4 | [STOF Receive Offset](#stof-receive-offset) | Public structure; units and semantics assumed |
| `0x20 + M` | 4 | [STOF Datapump Offset](#stof-datapump-offset) | Public structure; units and semantics assumed |
| `0x24 + M` | 4 | [Vertical Parity Check](#vertical-parity-check) | Public structure; calculation defined by working assumption |

The logical ASM size represented by this table is:

```text
ASM header       16 bytes
payload header    8 bytes
application data  M bytes
packet trailer   16 bytes
                 --------
total            M + 40 bytes
```

For the current `M = 92` profile, `P = 100` (`0x64`) and the complete logical
ASM region is 132 bytes (`0x84`), excluding IEEE-1394 framing and CRCs.

## ASM header

### Message ID

`message_id` is a `u32be` value that identifies the application message and
selects its payload definition. The current profile uses `0x00005D04`.

Working assumptions:

- all 32 bits participate in VPC;
- the value is stable for one application definition; and
- application selection may use additional profile metadata, so Message ID
  alone is not guaranteed globally unique.

### Reserved/security word

`reserved_security` is retained as a raw `u32be`. Its bit-level security and
reserved-field allocation is profile-defined and is not currently available.
The current profile reconstructs this word as `0x00000000`. A future profile
definition replaces that constant without changing the VPC word order.

### Node ID

`node_id` is retained as a raw `u32be` identifying the originating AS5643 node
according to the network profile. Its internal bit allocation is not currently
defined. The current profile reconstructs it as `0x00000000`.

### Priority and payload length

`priority_and_payload_length` is a `u32be` word. Aero1394 assumes this layout:

```text
bits 31..24  message_priority      u8
bits 23..0   payload_length_bytes  u24
```

`payload_length_bytes` counts Health Status, Heartbeat, and application data.
It excludes the four-word ASM header, the four-word packet trailer, and all
IEEE-1394 headers and CRCs. Therefore:

```text
payload_length_bytes = 8 + application_data_length
application_data_length = payload_length_bytes - 8
```

The current profile assumes priority zero and a 92-byte application payload,
so this header word is `0x00000064` and declares 100 protected payload bytes.
Values below 8 are invalid. Aero1394 requires the resulting application length
to be divisible by four for the current word-oriented VPC calculation.

## Payload header

### Health Status

Health Status is message-data word 0 and is represented as a raw `u32be`.
Public AS5643 material identifies it as node-level health information, while
the authoritative bit allocation belongs to the selected revision and network
profile.

The current profile applies these assumptions:

- `0x00000000` means that the node asserts no health conditions;
- every nonzero value is preserved and reported as an uninterpreted status
  bitmask until a profile supplies bit names; and
- all 32 bits participate in VPC exactly as transmitted.

Health Status is protocol metadata and is not part of application byte zero.

### Heartbeat

Heartbeat is message-data word 1 and is represented as a modulo-`2^32`
unsigned counter. It is generated by the message-producing application to show
that fresh data continues to be produced.

The current profile assumes:

- the producer increments Heartbeat by one whenever it places a new
  application data set into an ASM message;
- wrap from `0xFFFFFFFF` to `0x00000000` is valid;
- a delta of zero is a duplicate/stale-data finding;
- a modulo delta of one is consecutive fresh data; and
- a modulo delta greater than one is a sequence-gap finding, not a framing
  error. Raw values are always retained.

The observed sequence

```text
049CBDEE
049CBF8E   delta 416
049CC149   delta 443
049CC304   delta 443
```

does not satisfy the assumed consecutive-message rule. Aero1394 nevertheless
decodes the word as Heartbeat and reports the sequence discrepancy. Possible
causes include omitted messages, a producer-specific increment policy, or a
transformed stored representation.

## Application data

Application data begins immediately after Heartbeat. AS5643 owns its length
and its inclusion in VPC, but not its program-specific field meanings. The
current profile contains exactly 92 application bytes; those bytes are decoded
using [`PAYLOADS.md`](PAYLOADS.md) with application offset zero corresponding
to logical ASM offset `0x18`.

The current VPC contract treats application data as a sequence of `u32be`
words. A profile with a non-multiple-of-four application length requires an
explicit padding rule before VPC can be checked.

## Packet trailer

The packet trailer contains four consecutive `u32be` words. The first three
describe STOF-relative timing; the fourth protects the logical ASM contents.

### STOF Transmit Offset

`stof_transmit_offset` is the scheduled time from the applicable Start of
Frame event to message transmission. Aero1394 assumes an unsigned `u32be`
value with one microsecond per least-significant bit. The current profile value
is `1400`, interpreted as 1,400 microseconds after STOF.

The configured offset must be less than the selected STOF frame period. It is
schedule metadata, not a measurement derived from the capture timestamp.

### STOF Receive Offset

`stof_receive_offset` is the receiver-side STOF-relative reference used to
verify or schedule message reception. Aero1394 assumes an unsigned `u32be`
value with one microsecond per least-significant bit. The current profile value
is `500`, interpreted as 500 microseconds after STOF.

No ordering relationship between transmit and receive offsets is enforced
until the network profile defines the direction and node roles for the message.

### STOF Datapump Offset

`stof_datapump_offset` is the STOF-relative time at which the received message
is expected to be made available to the consuming application. Aero1394
assumes an unsigned `u32be` value with one microsecond per least-significant
bit. The current profile value is `500`, interpreted as 500 microseconds after
STOF.

No latency is calculated by subtracting the three STOF offsets unless the
network profile establishes that they share the same node, direction, and
frame reference.

### Vertical Parity Check

VPC is the final `u32be` word in the AS5643 packet trailer. Aero1394 assumes
that it is the bitwise complement of the XOR of every preceding 32-bit ASM word
from Message ID through STOF Datapump Offset. It excludes the VPC word itself,
the IEEE-1394 header and header CRC, and the IEEE-1394 data CRC.

For words `w[0]` through `w[n-1]` preceding VPC:

```text
xor_value = 0x00000000
for word in w:
    xor_value = xor_value XOR word
expected_vpc = NOT xor_value       // masked to 32 bits
```

For the current profile, the reconstructed ASM-header inputs are:

| Header word | Value |
| --- | ---: |
| Message ID | `0x00005D04` |
| Reserved/security | `0x00000000` |
| Node ID | `0x00000000` |
| Priority/payload length | `0x00000064` |
| Header XOR | `0x00005D60` |

Let `visible_xor` be the XOR of Health Status, Heartbeat, every application
word, and all three STOF-offset words. The assumed current-profile calculation
is therefore:

```text
expected_vpc = NOT (visible_xor XOR 0x00005D60)
             = (NOT visible_xor) XOR 0x00005D60
```

Every complete fixture checked satisfies that relationship. Validation returns:

| Result | Meaning |
| --- | --- |
| `Valid` | Stored VPC equals the calculated VPC under the selected profile. |
| `Invalid` | Stored and calculated VPC values differ. |
| `NotPresent` | The logical message has no complete VPC word. |
| `NotChecked` | Required words, alignment, or profile inputs are unavailable. |

A result produced with reconstructed header constants must also carry
`assumption_dependent = true`. Raw VPC, calculated VPC, selected profile, and
all reconstruction inputs remain available to callers.

## Timing model

AS5643 frame timing, capture sampling, and application production are separate
time domains. Public DAP material describes STOF at a network-profile-specific
rate, typically 80 Hz or 100 Hz, and ASM transmission at assigned offsets from
STOF. The current one-microsecond offset resolution is an Aero1394 working
assumption.

Acquisition cadence belongs to input provenance and application production
timing belongs to the applicable payload definition. A decoder does not infer
one rate from another or synthesize missing protocol events on an ideal grid.

## Assumptions requiring confirmation

- the producing system's exact AS5643 revision and network-profile slash sheet;
- big-endian encoding for every logical ASM word after reconstruction;
- the priority/payload-length bit split;
- the reserved/security and Node ID bit allocations and current zero values;
- Health Status bit meanings and the zero-value interpretation;
- Heartbeat initialization and increment policy;
- one-microsecond STOF-offset resolution and the precise receive/datapump
  semantics;
- the VPC word range, alignment/padding rules, and reconstructed header inputs;
  and
- known-good and known-bad messages from an independent AS5643 decoder.
