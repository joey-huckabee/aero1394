# SAE AS5643 protocol evidence

- Status: Protocol contract deferred pending authoritative evidence
- Last updated: 2026-08-28
- Scope: AS5643 interpretation independent of any capture container

## Purpose

This document owns Aero1394's AS5643 protocol contract. It will define the
supported AS5643 message forms, field and bit layout, integrity coverage,
status and heartbeat semantics, timing fields, and unsupported cases once
those details are supported by an identified revision and controlled evidence.

## Boundary

AS5643 is interpreted only after a supported IEEE-1394 representation has been
identified:

```text
IEEE-1394 packet or transaction
    -> optional AS5643 message
        -> opaque application payload
```

[`IEEE1394.md`](IEEE1394.md) owns the IEEE-1394 wire representation, packet
families, byte and bit numbering, and applicable IEEE CRCs. This document owns
only the AS5643 layer. [`PAYLOADS.md`](PAYLOADS.md) begins at application byte
zero and owns program-specific field meanings.

An AS5643 decoder must consume a supported IEEE-1394 result without depending
on the source capture container or an application-payload definition. Traffic
that is not AS5643, or cannot yet be identified as AS5643, must remain
inspectable at the IEEE-1394 layer.

## Current evidence gap

The exact applicable AS5643 revision and an authorized normative source have
not been established. No controlled input currently provides both a complete,
identified IEEE-1394 representation and an independent AS5643 decode of the
same event. Candidate field positions seen in downstream stored bytes are not
sufficient to define AS5643 byte layout or validation behavior.

Consequently, Aero1394 does not yet define a normative AS5643 message grammar
or claim that any observed word is a confirmed health, heartbeat, Start of
Frame (STOF), or Vertical Parity Check (VPC) field.

## Future decoder contract

When the evidence gate is met, this document will define:

- the supported IEEE-1394 packet or transaction forms that may carry AS5643;
- the positive identification rules for an AS5643 message;
- the applicable AS5643 revision and explicit byte/bit numbering convention;
- message identity, node, security, priority, size, and other applicable
  header fields;
- health-status, heartbeat, STOF, and other applicable status or timing fields;
- VPC or other integrity-field coverage, ordering, and result states;
- the exact boundary at which application byte zero begins; and
- behavior for unknown, unsupported, truncated, and invalid messages.

Any stable API must use neutral names for unconfirmed fields. Integrity results
must distinguish at least valid, invalid, not present, and not checked; a
plausible calculation is not a normative validation result.

## Timing boundary

AS5643 frame timing, capture sampling, and application production are separate
time domains. This document will own protocol-defined frame timing after the
selected revision establishes it. Acquisition cadence belongs to the input
source's provenance, while application production timing belongs to the
applicable payload definition. A decoder must not infer one rate from another
or synthesize missing protocol events from an ideal time grid.

## Evidence required to define the decoder

- the authoritative AS5643 revision and permission to use its definitions;
- controlled IEEE-1394 packets with known AS5643 interpretations;
- an independent analyzer or vendor decode of the same events;
- known message IDs, payload sizes, node/security/priority values, and field
  encodings;
- controlled health-status and heartbeat sequences;
- known STOF and message-timing cases at each supported frame rate;
- known-good and known-bad VPC examples with confirmed coverage and byte/bit
  ordering; and
- examples of non-AS5643, unsupported, truncated, and malformed traffic.

## Current conclusion

No AS5643 decoder behavior is currently specified. Protocol-like observations
from a particular input representation remain evidence about that input until
they can be correlated with a complete IEEE-1394 event and the selected AS5643
revision.
