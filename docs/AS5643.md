# SAE AS5643 ASM profile

- Status: Provisional implementation contract based on explicit working assumptions
- Last updated: 2026-08-30
- Assumed base revision: SAE AS5643B; producing-system revision not confirmed
- Scope: AS5643 Anonymous Subscriber Message interpretation independent of capture format

## Purpose

This document defines the AS5643 Anonymous Subscriber Message (ASM) profile
used by Aero1394. It owns the logical ASM header, payload header, application
boundary, packet trailer, heartbeat behavior, STOF-relative timing fields, and
Vertical Parity Check (VPC) calculation. Input-container documents may map
stored bytes to these fields, but they do not redefine their AS5643 semantics.

SAE describes AS5643B as the base specification for data-bus characteristics,
data formats, and node operation, with vehicle-specific details delegated to a
network-profile slash sheet. Public SAE and DAP Technology material establishes
the structure and timing rules cited below. The applicable producer revision,
complete base-standard text, and network-profile slash sheet are not yet
available, so the remaining assumptions stay explicit and testable.

## Implementation status

The `v0.2.0` library module `as5643` implements raw decoding for the retained
116-byte payload/trailer representation under profile
`aero1394-assumed-as5643b-v1`. The API requires an explicit AS5643 Message ID,
returns the profile ID and assumption-dependent marker, exposes the
reconstructed raw header words and all retained raw fields, borrows the exact
92 application bytes, and preserves the complete input. It calculates VPC from
explicit reconstructed header inputs and returns an auditable structured
validation result.

The current implementation does not select the profile from a BIE record,
decode application fields, or represent an IEEE-1394 wire packet. Those remain
separate downstream increments.

Definitions below use these labels:

| Label | Meaning |
| --- | --- |
| Public structure | Shown by the official SAE description or DAP Technology's public AS5643 material |
| Working assumption | Aero1394 behavior selected to make the current profile implementable |
| Profile-defined | A value whose authoritative meaning ultimately belongs to the vehicle network profile |

## Protocol boundary

AS5643 interpretation begins with the logical ASM header carried by a supported
IEEE-1394 asynchronous-stream representation and ends after the AS5643 packet
trailer:

```text
IEEE-1394 asynchronous-stream packet
    -> AS5643 ASM header
        -> AS5643 payload header
            -> opaque application data
        -> AS5643 packet trailer
    -> IEEE-1394 data CRC
```

[`IEEE1394.md`](IEEE1394.md) owns the surrounding IEEE-1394 representation,
packet fields, and IEEE CRCs. [`PAYLOADS.md`](PAYLOADS.md) owns the application
data beginning at application offset zero. AS5643 decoding does not depend on
the source capture container or on a known application definition.

## Profile identity and selection

The profile defined by this document has the stable provisional identifier:

```text
aero1394-assumed-as5643b-v1
```

Every decoded result produced by this profile carries that identifier and
`assumption_dependent = true`. Profile selection must be explicit or based on
an input mapping that names this identifier; byte-pattern recognition alone is
insufficient. A later authoritative profile receives a new identifier rather
than silently changing these assumptions.

## Logical ASM layout

DAP Technology's public AS5643 layout shows a four-word ASM header, Health
Status as message-data word 0, Heartbeat as message-data word 1, application
message data, three STOF-offset trailer words, and VPC. Aero1394 represents
each AS5643 word as one big-endian unsigned 32-bit integer.

Let `M` be the application-data length in bytes and `P = M + 8` be the AS5643
payload length, including Health Status and Heartbeat. Logical offsets below
start at ASM-header word 0 and exclude the surrounding IEEE-1394 header, header
CRC, and data CRC.

| Logical ASM offset | Width | Field | Status |
| ---: | ---: | --- | --- |
| `0x00` | 4 | [Message ID](#message-id) | Public structure; captured BIE mapping is `u32be` |
| `0x04` | 4 | [Reserved/security word](#reservedsecurity-word) | Public structure; bit allocation profile-defined |
| `0x08` | 4 | [Node ID](#node-id) | Public structure; bit allocation profile-defined |
| `0x0C` | 4 | [Priority and payload length](#priority-and-payload-length) | Public structure; bit split is a working assumption |
| `0x10` | 4 | [Health Status](#health-status) | Public structure; bit allocation profile-defined |
| `0x14` | 4 | [Heartbeat](#heartbeat) | Public structure; freshness use established, increment policy producer-defined |
| `0x18` | `M` | [Application data](#application-data) | Profile-defined |
| `0x18 + M` | 4 | [STOF Transmit Offset](#stof-transmit-offset) | Public structure; 1 us resolution, assignment profile-defined |
| `0x1C + M` | 4 | [STOF Receive Offset](#stof-receive-offset) | Public structure; 1 us resolution, precise semantics profile-defined |
| `0x20 + M` | 4 | [STOF Datapump Offset](#stof-datapump-offset) | Public structure; 1 us unit and precise semantics assumed |
| `0x24 + M` | 4 | [Vertical Parity Check](#vertical-parity-check) | Public structure; calculation fixture-confirmed with reconstructed inputs |

The logical ASM size represented by this table is:

```text
ASM header       16 bytes
payload header    8 bytes
application data  M bytes
packet trailer   16 bytes
                 --------
total            M + 40 bytes
```

For the current `M = 92` profile, `P = 100` (`0x64`) and the complete logical
ASM region is 132 bytes (`0x84`), excluding IEEE-1394 framing and CRCs.

## ASM header

### Message ID

`message_id` is a `u32be` value that identifies the application message and
selects its payload definition. The current profile uses `0x00005D04`.

Message ID is an AS5643 ASM-header field, not a field invented by BIE. The BIE
record also begins with its own `data_item_id` container field. For the current
record family, BIE omits the four-word ASM header and carries the value needed
to reconstruct its Message ID in `data_item_id`:

```text
BIE data_item_id 0x00005D04
    -> reconstructed AS5643 message_id 0x00005D04
        -> msfcs_storesmassdata_b payload definition
```

The bytes at BIE record offset zero therefore belong to BIE framing, while the
logical field reconstructed from them belongs to AS5643. They are one mapped
identity in this record family, not two independently observed identifiers.

Working assumptions:

- all 32 bits participate in VPC;
- the value is stable for one application definition; and
- application selection may use additional profile metadata, so Message ID
  alone is not guaranteed globally unique.

### Reserved/security word

`reserved_security` is retained as a raw `u32be`. Its bit-level security and
reserved-field allocation is profile-defined and is not currently available.
The current profile reconstructs this word as `0x00000000`. A future profile
definition replaces that constant without changing the VPC word order.

### Node ID

`node_id` is retained as a raw `u32be` identifying the originating AS5643 node
according to the network profile. Its internal bit allocation is not currently
defined. The current profile reconstructs it as `0x00000000`.

### Priority and payload length

`priority_and_payload_length` is a `u32be` word. Aero1394 assumes this layout:

```text
bits 31..24  message_priority      u8
bits 23..0   payload_length_bytes  u24
```

`payload_length_bytes` counts Health Status, Heartbeat, and application data.
It excludes the four-word ASM header, the four-word packet trailer, and all
IEEE-1394 headers and CRCs. Therefore:

```text
payload_length_bytes = 8 + application_data_length
application_data_length = payload_length_bytes - 8
```

The current profile assumes priority zero and a 92-byte application payload,
so this header word is `0x00000064` and declares 100 protected payload bytes.
Values below 8 are invalid. Aero1394 requires the resulting application length
to be divisible by four for the current word-oriented VPC calculation.

## Payload header

### Health Status

Health Status is message-data word 0 and is represented as a raw `u32be`.
Public AS5643 material identifies it as node-level health information, while
the authoritative bit allocation belongs to the selected revision and network
profile.

The current profile applies these assumptions:

- `0x00000000` means that the node asserts no health conditions;
- every nonzero value is preserved and reported as an uninterpreted status
  bitmask until a profile supplies bit names; and
- all 32 bits participate in VPC exactly as transmitted.

Health Status is protocol metadata and is not part of application byte zero.

### Heartbeat

Heartbeat is message-data word 1 and is represented as a `u32be` freshness
count. Public DAP material describes it as a producer-generated count monitored
to determine that the node is operational and sending fresh data. It does not
establish that every producer must use a consecutive packet sequence.

The current profile therefore applies these rules:

- a delta of zero is a duplicate/stale-data finding;
- a nonzero delta shows that the producer changed the freshness value;
- the raw value and modulo-`2^32` delta are retained for analysis; and
- delta magnitude is not converted into a dropped-message count or sequence-gap
  finding without a producer definition.

The final-fixture sequence is:

```text
049CBDEE
049CBF8E   delta 416
049CC149   delta 443
049CC304   delta 443
```

The values are neither random nor tied directly to the BIE sampling cadence.
Across the first and final known-good capture records:

```text
heartbeat delta             = 378,722 counts
recorder elapsed time       = 14.6 seconds
empirical heartbeat rate    = 25,939.86 counts/second

payload system-tick delta   = 198,523,629,520 ticks
ticks per heartbeat count   = 524,193.55
2^19                        = 524,288
```

The provided payload-clock calculation is `106.25e6 * 2^7`, exactly 13.6 GHz,
with one system-tick LSB equal to `1 / (106.25e6 * 2^7)`, or approximately
73.5294 picoseconds. Dividing that clock by `2^19` gives:

```text
13,600,000,000 / 2^19 = 25,939.94140625 counts/second
at 60 Hz              =    432.3324 counts/payload
at 80 Hz              =    324.2493 counts/sample attempt
at 100 Hz             =    259.3994 counts/STOF frame
```

The 60 Hz result explains the observed deltas near 432. It does not indicate
that the Heartbeat is driven by the 80 Hz FireSpy sampling cadence or by a
possible 100 Hz STOF rate.

For all eight fixtures, Heartbeat is close to the low 32 bits of
`system_ticks >> 19`, with a difference of 29 to 103 counts. This is strong
evidence that the two fields derive from the same producer clock family and
are sampled at different processing points. It is not evidence that AS5643
defines a 25.94 kHz Heartbeat clock. Aero1394 will treat that relationship as a
capture-specific analysis hypothesis, not a generic protocol rule.

## Application data

Application data begins immediately after Heartbeat. AS5643 owns its length
and its inclusion in VPC, but not its program-specific field meanings. The
current profile contains exactly 92 application bytes; those bytes are decoded
using [`PAYLOADS.md`](PAYLOADS.md) with application offset zero corresponding
to logical ASM offset `0x18`.

The current VPC contract treats application data as a sequence of `u32be`
words. A profile with a non-multiple-of-four application length requires an
explicit padding rule before VPC can be checked.

## Packet trailer

The packet trailer contains four consecutive `u32be` words. The first three
describe STOF-relative timing; the fourth protects the logical ASM contents.

### Start of Frame and offset unit

The AS5643 Control Computer transmits a Start of Frame (STOF) packet to mark
the beginning of each fixed-duration network frame. Nodes synchronize to that
event and use network-profile-assigned offsets to schedule transmission and
reception. AS5643 defines transmit and receive offsets in one-microsecond
increments. The current profile applies the same unit to the Datapump Offset;
that unit remains to be confirmed from the complete definition.

The two frame rates relevant to the supplied environment correspond to:

| Frame rate | Frame period |
| ---: | ---: |
| 80 Hz | 12,500 us |
| 100 Hz | 10,000 us |

The captured trailer values `1400/500/500` are within either frame period.
They are STOF-relative timing metadata carried with the message, not the BIE
recorder timestamp and not the Heartbeat clock.

### STOF Transmit Offset

`stof_transmit_offset` is the scheduled time from the applicable Start of
Frame event to message transmission. It is an unsigned `u32be` value with one
microsecond per least-significant bit. The current profile value is `1400`, so
the message is assigned to transmit 1.4 milliseconds after STOF.

The configured offset must be less than the selected STOF frame period. It is
schedule metadata, not a measurement derived from the capture timestamp.

### STOF Receive Offset

`stof_receive_offset` is the receiver-side STOF-relative reference used to
verify or schedule message reception. It is an unsigned `u32be` value with one
microsecond per least-significant bit. The current profile value is `500`.

The capture establishes the value and unit, but the missing network profile is
still required to determine the applicable receiver, timing window, and exact
relationship to the transmit assignment. Aero1394 therefore does not reject
the value merely because it is numerically less than `1400`.

### STOF Datapump Offset

`stof_datapump_offset` is the STOF-relative time at which the received message
is expected to be made available to the consuming application. It is retained
as an unsigned `u32be`; the current profile interprets it in one-microsecond
units. The current profile value is `500`.

No latency is calculated by subtracting the three STOF offsets unless the
network profile establishes that they share the same node, direction, and
frame reference.

### Vertical Parity Check

VPC is the final `u32be` word in the AS5643 packet trailer. Aero1394 assumes
that it is the bitwise complement of the XOR of every preceding 32-bit ASM word
from Message ID through STOF Datapump Offset. It excludes the VPC word itself,
the IEEE-1394 header and header CRC, and the IEEE-1394 data CRC.

For words `w[0]` through `w[n-1]` preceding VPC:

```text
xor_value = 0x00000000
for word in w:
    xor_value = xor_value XOR word
expected_vpc = NOT xor_value       // masked to 32 bits
```

For the current profile, the reconstructed ASM-header inputs are:

| Header word | Value |
| --- | ---: |
| Message ID | `0x00005D04` |
| Reserved/security | `0x00000000` |
| Node ID | `0x00000000` |
| Priority/payload length | `0x00000064` |
| Header XOR | `0x00005D60` |

Let `visible_xor` be the XOR of Health Status, Heartbeat, every application
word, and all three STOF-offset words. The assumed current-profile calculation
is therefore:

```text
expected_vpc = NOT (visible_xor XOR 0x00005D60)
             = (NOT visible_xor) XOR 0x00005D60
```

Every complete fixture checked satisfies that relationship. Validation returns:

| Result | Meaning |
| --- | --- |
| `Valid` | Stored VPC equals the calculated VPC under the selected profile. |
| `Invalid` | Stored and calculated VPC values differ. |
| `NotPresent` | The logical message has no complete VPC word. |
| `NotChecked` | Required words, alignment, or profile inputs are unavailable. |

A result produced with reconstructed header constants must also carry
`assumption_dependent = true`. Raw VPC, calculated VPC, selected profile, and
all reconstruction inputs remain available to callers.

The Rust API represents the four header words and the retained byte range with
`VpcCalculationInputs`. `calculate_vpc` rejects protected data that is not
32-bit-word aligned. `validate_vpc` returns a `VpcValidation` containing the
outcome, optional stored and calculated values, available input evidence, and a
reason when an available VPC could not be checked. A decoded current-profile
message supplies `vpc_validation` as the direct checked path; the general API
retains `NotPresent` and `NotChecked` for incomplete or unsupported inputs.

## How Aero1394 will use these fields

The known-good BIE values are suitable decoder and analysis inputs. The
distinction below concerns how Aero1394 uses each field, not whether the
captured bytes are trustworthy.

| Field | Aero1394 use |
| --- | --- |
| Message ID | Select an ASM profile and application payload definition. For BIE, reconstruct it from `data_item_id`. |
| Reserved/security | Preserve the reconstructed word and include it in VPC. Do not assign security-bit meanings without the network profile. |
| Node ID | Identify the source node after its bit allocation is supplied; until then retain the reconstructed word. |
| Priority/payload length | Validate application boundaries and declared size; expose priority only under the selected bit layout. |
| Health Status | Report the captured node-health word and later decode named conditions from the network profile. |
| Heartbeat | Detect unchanged/stale application data and expose count/rate trends. Do not infer lost messages from delta magnitude. |
| Application data | Dispatch the 92 bytes to the selected built-in payload decoder without mixing program fields into AS5643. |
| STOF Transmit Offset | Check the configured transmit slot and, when a capture contains a usable STOF time reference, compare actual transmission timing with the 1,400 us assignment and profile tolerance. |
| STOF Receive Offset | Support receive-window verification after the receiver role and allowed tolerance are available. |
| STOF Datapump Offset | Support application-availability timing after the datapump reference and node role are available. |
| VPC | Detect data corruption, wrong boundaries, wrong byte order, or an incorrect reconstructed header. It does not correct data, authenticate a sender, or replace IEEE-1394 CRC validation. |

For current BIE-only decoding, the STOF words are reported and range-checked
against a selected frame period. Absolute schedule compliance requires the
corresponding STOF event or another verified frame-time anchor; the recorder
timestamp alone is not silently treated as that anchor. VPC can be checked now
because every required retained word and the profile's reconstructed header
inputs are available.

## Timing model

AS5643 frame timing, capture sampling, and application production are separate
time domains. Public DAP material describes STOF at a network-profile-specific
rate, typically 80 Hz or 100 Hz, and ASM transmission at assigned offsets from
STOF. AS5643 defines transmit and receive offset resolution as one microsecond;
the current profile applies that resolution to the Datapump Offset as well.

Acquisition cadence belongs to input provenance and application production
timing belongs to the applicable payload definition. A decoder does not infer
one rate from another or synthesize missing protocol events on an ideal grid.

## Assumptions requiring confirmation

- the producing system's exact AS5643 revision and network-profile slash sheet;
- big-endian encoding for every logical ASM word after reconstruction;
- the priority/payload-length bit split;
- the reserved/security and Node ID bit allocations and current zero values;
- Health Status bit meanings and the zero-value interpretation;
- Heartbeat initialization and increment policy;
- the Datapump Offset unit and precise receive/datapump semantics, roles, and
  tolerances;
- the VPC word range, alignment/padding rules, and reconstructed header inputs;
  and
- known-good and known-bad messages from an independent AS5643 decoder.
