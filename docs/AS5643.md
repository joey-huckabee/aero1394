# AS5643-derived record evidence

- Status: Preliminary evidence; no normative AS5643 decoder implemented
- Last updated: 2026-08-28
- Scope: downstream protocol observations for the currently supplied message

## Boundary

This document isolates AS5643-related observations from both the generic BIE
container and application payload definitions:

```text
BIE container -> opaque stored data -> AS5643-derived envelope -> application payload
```

`BIE-FORMAT.md` stops at the opaque stored-data boundary. `PAYLOADS.md` begins
at application byte zero. This document owns the provisional words and trailer
between those boundaries.

The observed representation is not a complete IEEE-1394 wire packet. No
IEEE-1394 link header, header CRC, four-word ASM header, or IEEE-1394 data CRC
has been identified in the stored bytes. BIE may strip or normalize those
fields. That hypothesis must not be generalized to another BIE variant without
evidence.

## Observed envelope

For the currently supplied message, the BIE stored-data region is 116 bytes.
Offsets below are relative to the beginning of stored data, not the BIE record:

| Stored-data offset | Width | Interpretation | Evidence |
| ---: | ---: | --- | --- |
| `0x00` | 4 | Protocol word 0; health-status position candidate | Inferred; observed value is zero |
| `0x04` | 4 | Protocol word 1; heartbeat position candidate | Position inferred; behavior contradicts the expected `+1` heartbeat |
| `0x08` | 92 | Application bytes | **Confirmed** by independent summary size and field alignment |
| `0x64` | 4 | STOF transmit-offset candidate, observed `1400` | Strong inference |
| `0x68` | 4 | STOF receive-offset candidate, observed `500` | Strong inference |
| `0x6C` | 4 | STOF datapump-offset candidate, observed `500` | Strong inference |
| `0x70` | 4 | VPC candidate | Strong inference from repeated XOR/complement behavior |

The byte accounting is exact:

```text
protocol words           8
application payload     92
three STOF words        12
VPC                      4
                        ---
stored data            116 (0x74)
```

## Heartbeat discrepancy

AS5643 places Health Status and Heartbeat ahead of message data, which makes
the first two stored words structurally attractive candidates. The second word
does not exhibit a simple heartbeat increment. Near the end of the supplied
recording it changes as follows:

```text
049CBDEE
049CBF8E   delta 416
049CC149   delta 443
049CC304   delta 443
```

Therefore the stable API must retain neutral names such as `protocol_word_0`
and `protocol_word_1`. Plausible explanations remain:

- BIE transforms or replaces the original heartbeat;
- the producing system does not follow the expected heartbeat behavior;
- the supplied size has a different protocol meaning; or
- another proprietary normalization layer exists.

## VPC evidence and missing-header hypothesis

For every complete record checked, complementing the XOR of all visible words
from protocol word 0 through the third STOF word produces a value whose XOR
difference from the stored VPC is the same:

```text
visible calculation XOR stored VPC = 0x00005D60
```

For this message, that residual also equals:

```text
data_item_id                 0x00005D04
XOR protected payload size  0x00000064  (92 + 8)
                             ----------
                             0x00005D60
```

This is strong evidence that the VPC protects an original AS5643 packet whose
four-word ASM header is absent or normalized in BIE storage. Message ID and
protected payload size explain the observed residual exactly. Security, node,
priority, and their encodings remain unknown; they may be zero, cancel under
XOR, or be represented elsewhere.

The repository tests preserve the residual as evidence. They do not report the
VPC as normatively valid until the missing header inputs and selected AS5643
revision are established.

## Recorder cadence

FireSpy operation uses an 80 Hz or 100 Hz recorder cadence according to its
configuration. Recorder timestamps in the supplied sample fall on a 12.5 ms
grid, so this capture is consistent with the 80 Hz case. Observed gaps include
12.5 ms and 25 ms.

The application payload happens to be produced at 60 Hz on this platform. That
rate is not how FireSpy operates and does not establish a protocol-defined
60 Hz/80 Hz scheduling relationship. The payload-specific rate and its evidence
are documented in `PAYLOADS.md`.

## Required confirmation

- the authoritative AS5643 revision and permitted implementation source;
- the exact meaning and encoding of both pre-payload words;
- the four omitted ASM-header words, including node, security, and priority;
- the normative VPC word range and byte/bit ordering;
- known-good and known-bad VPC examples from an independent decoder;
- records with different message IDs and protected payload sizes; and
- controlled heartbeat, STOF, missing-message, and 80 Hz/100 Hz recorder cases.
