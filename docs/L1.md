# Aero1394 — Level 1 requirements

- Status: Baseline for staged implementation
- Last updated: 2026-08-28

## Purpose

This document defines the highest-level product outcomes for Aero1394. Level 1
(L1) requirements state what the product must do without prescribing module,
wire-field, or test-fixture details. [Level 2 requirements](L2.md) decompose
these outcomes into architectural behavior, and [Level 3 requirements](L3.md)
decompose that behavior into directly verifiable obligations.

Live implementation status and verification artifacts are maintained in the
auto-generated [requirements trace matrix](TRACE-MATRIX.md).

## Scope and conventions

Each requirement has a permanent identifier of the form
`L1-<CATEGORY>-<NNN>`. Statements use **SHALL** for mandatory behavior.
Verification methods are Test (`T`), Analysis (`A`), Inspection (`I`),
Demonstration (`D`), and comparison with independent Evidence (`E`).

The requirements remain bounded by the evidence in `BIE-FORMAT.md`,
`IEEE1394.md`, `AS5643.md`, and `PAYLOADS.md`. A supported observed variant is
not implicitly a claim about every file or platform using a similar name.

| Code | Area |
| --- | --- |
| `BIE` | BIE container and record decoding |
| `TIM` | Recorder and payload time domains |
| `PRO` | Protocol-envelope and integrity handling |
| `PAY` | Built-in application payload decoding |
| `OUT` | Canonical data and output adapters |
| `TST` | Verification evidence and fixtures |

## L1-BIE: BIE container and record decoding

### L1-BIE-001

**Statement**: Aero1394 SHALL safely decode supported BIE recording variants
into bounded records while preserving the raw bytes, source offsets, and
unrecognized data needed for forensic inspection.

**Rationale**: BIE framing is the first required input boundary. The format is
not fully documented, so useful evidence must survive even when a record or
downstream layout is not recognized.

**Verification Method**: T, E

## L1-TIM: Recorder and payload time domains

### L1-TIM-001

**Statement**: Aero1394 SHALL preserve and correctly represent confirmed time
domains without conflating recorder calendar time, payload system ticks, or
platform scheduling rates.

**Rationale**: Recorder timestamps and application ticks have different
origins and evidence. Treating one as the other can silently corrupt ordering,
elapsed-time calculations, and exported data.

**Verification Method**: T, E

## L1-PRO: Protocol-envelope and integrity handling

### L1-PRO-001

**Statement**: Aero1394 SHALL expose BIE stored data independently of
downstream decoding and SHALL preserve evidence-qualified protocol-envelope
and integrity information when a supported interpretation is available.

**Rationale**: Container decoding must remain useful without IEEE-1394,
AS5643, or application knowledge, while later layers still need a safe place to
report provisional and validated protocol findings.

**Verification Method**: T, E

## L1-PAY: Built-in application payload decoding

### L1-PAY-001

**Statement**: Aero1394 SHALL decode supported application payloads through
versioned Rust definitions compiled into the tool, without requiring runtime
YAML profiles, and SHALL preserve unsupported payloads as raw data.

**Rationale**: Program-specific structures must be type checked, reviewable,
and independently extensible without contaminating generic BIE or protocol
parsing.

**Verification Method**: T, I

## L1-OUT: Canonical data and output adapters

### L1-OUT-001

**Statement**: Aero1394 SHALL retain a lossless canonical representation from
which stable human-readable and machine-readable outputs can be produced.

**Rationale**: Formatting and adapter choices must not discard wire values or
become the internal data model. CLI, CSV, Parquet, and Python consumers should
derive from the same decoded meaning.

**Verification Method**: T, I

## L1-TST: Verification evidence and fixtures

### L1-TST-001

**Statement**: Aero1394 SHALL maintain reproducible, provenance-bearing, and
appropriately sanitized verification evidence for each implemented decoding
layer.

**Rationale**: Reverse-engineered format claims require reviewable evidence,
boundary cases, and tests without committing restricted source captures.

**Verification Method**: T, I, E
